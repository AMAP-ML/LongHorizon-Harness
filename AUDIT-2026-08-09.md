# Kusudaemon architecture audit — 2026-08-09

Findings from reading `src/kusudaemon/` end to end, ordered by how much they
cost you. Each entry: what's wrong, the evidence, and the tradeoff of fixing it.

Sections 1–5 are quality defects (the harness produces worse output than its
design implies). Sections 6–11 are efficiency defects (it spends tokens, calls,
or wall-clock it doesn't need to).

---

## 1. The artifact is the agent's closing chat message, not its work

**`v0/runner.py:117-119`**

```python
artifact_text = result.metadata.get("assistant_visible_output") or result.actions_log or ""
artifact_path.write_text(artifact_text, encoding="utf-8")
```

`assistant_visible_output` is `gptme_visible_output`'s *last assistant message*
(`adapters/gptme_adapter.py`). Meanwhile nothing in the writer's prompt ever
tells it that its final message is the deliverable:

- `pipeline/prompts.py:build_node_prompt` → brief + contract + inputs + rubric.
  No artifact path, no output-format instruction.
- `v1/writer.py:_PROMOTION_INSTRUCTION_TEMPLATE` → only adds the
  `promotion.json` instruction.

A gptme writer with `save`/`patch` in its allowlist will do the natural thing:
write a file, then close with *"I've written the section to out/foo.md — let me
know if you'd like changes."* That sentence becomes `out/<node>.md`. It passes
`nonempty`. It passes `max_tokens:24000`. It gets concatenated into
`assembly/main.md`.

Worse: if the agent *does* write `out/<node>.md` correctly, line 119 overwrites
it with the chat message immediately after the episode.

This is almost certainly an oversight rather than a design choice, because
`v3/repair.py:build_repair_prompt` gets it right — it ends with *"Produce the
full corrected artifact text as your final answer."* The repair path knows the
contract; the primary writer path never got the same line.

**Fix options**
- Cheapest: append the same sentence `repair.py` uses to `writer_prompt()`.
- Better: instruct the writer to `save` to `out/<node>.md` and have `run_node`
  prefer that file when it exists, falling back to visible output.

**Pros** — this single change is the difference between the harness producing a
document and producing a transcript. Nothing downstream needs to move.
**Cons** — option 2 breaks v0's current invariant that `run_node` alone decides
artifact content, and introduces an ambiguity (agent wrote a *different* file,
or a partial one) that needs a rule. Option 1 keeps the whole artifact inside
one model response, which caps effective section length at the model's output
limit — fine for 1–3k-word leaves, not for anything longer.

## 2. Writers cannot reach the source corpus

**`v2/planner.py:add_leaf`** sets `inputs=[unit.id for unit in slice_units]` —
values like `"unit-03"`.
**`v2/survey.py:SpineUnit`** is `{id, label, start_chunk, end_chunk, tokens}`.
No text. `save_spine` persists exactly those fields.
**`pipeline/prompts.py`** then renders:

```
Inputs (read them with your tools before writing, and cite them where relevant):
- unit-03
```

There is no file named `unit-03` anywhere in the run directory, and no mapping
on disk from a unit to a byte range of `source.txt`. The chunk offsets that
would resolve it are recomputed in memory by `chunk_text` during the survey
phase and thrown away.

So every leaf writes its section from a ~60-character label and the global
contract. The entire survey → spine pipeline discovers structure that is never
reconnected to content. `pipeline/backends.py`'s docstring asserts the opposite
("the writer sees `source.txt` ... the entire corpus a leaf needs") — true of
the filesystem, but the writer is never told, and if it did `cat source.txt` it
would blow §8 context discipline and its own budget in one move.

**Fix** — materialize slices. Either write `spine/unit-03.md` during
`_phase_survey` and put those paths in `inputs`, or persist char offsets on
`SpineUnit` and have `build_node_prompt` emit
`source.txt#chars=12040-18830`.

**Pros** — restores the causal link the whole architecture is built around;
makes `inputs` mean what §6 says it means; costs zero model calls.
**Cons** — duplicates the corpus on disk (offsets avoid this but require the
agent to do arithmetic, which models do badly — materialized files are more
reliable). `SpineUnit` gains a field, so existing `spine.json` files need a
migration or a tolerant loader.

## 3. The Reviewer never runs, so `nonempty` is the real exit condition

`v2/planner.py:add_leaf` sets `gates = ["nonempty", "max_tokens:24000"]` and
leaves `judgment`/`rubric` at their empty defaults. `v1/reviewer.py:review_node`
opens with:

```python
if not node.judgment:
    return ReviewVerdict(node_id=node.id, items=[], verdict="pass")
```

And `_gate_exists` is documented as always-true. So in a real pipeline run the
complete verification apparatus for every leaf reduces to: *the file is not
empty and is under 24k tokens.* Combined with finding #1, "I've written the
section" satisfies it.

The reviewer, the verdict schema, the audit files, `max_attempts`, the
patchable/regenerate classification — all of it is live code that the default
planner output never reaches. This is the node-type template gap the codebase
already flags in three docstrings, but the practical consequence isn't recorded
anywhere: **the default path has no semantic quality bar at all.**

**Fix** — derive `judgment`/`rubric` per shape from the frozen contract at the
end of `_phase_pilot` (the contract is exactly the right source: it's the
generalized rules from the operator's own pilot edit). Even three shape-generic
rubric lines would turn the reviewer on.

**Pros** — activates ~600 lines of already-tested machinery; the retry loop and
the revalidation triage start doing something.
**Cons** — one reviewer call per leaf, so a 400-node tree gains 400 calls; and
a badly-derived rubric turns into spurious failures that burn `max_attempts` and
block nodes. Needs to ship with the rubric visible to the operator before
execute starts.

## 4. Retries throw away the reason for failure

**`v1/round_loop.py:_transition_after_writer` / `_transition_after_review`**

On a gate failure the unmet gates go into `events.jsonl` and `manifest.jsonl`.
On a review failure the verdict's located defects go into `audit/<node>.json`.
The node is then set back to `"pending"` and, when the orchestrator picks it up
again, redispatched with `prompt_for_node(node)` — byte-identical to attempt 1.

So attempts 2 and 3 are i.i.d. resamples. `max_attempts=3` buys you three rolls
of the same die, not a correction loop. `v1/gates.py`'s own docstring describes
the intended behavior — *"it fails the gate and gets `unmet: R3 (4 problems,
need 5)`"* — and that feedback is never delivered.

The mechanism to do this correctly already exists in `v3/repair.py`
(`build_repair_prompt` with the defect text and the current artifact); it's
simply not wired into the v1 retry path.

**Fix** — carry the last `GateResult` list / `ReviewVerdict` on the node (or
read them back from the audit file) and append them to the retry prompt.

**Pros** — retries become informed; a `len:800-1200` miss self-corrects in one
turn instead of one-in-three by luck. Nearly free.
**Cons** — the retry prompt is no longer identical to the fresh prompt, so
`run_node`'s "resume from the original prompt" story gets a caveat; and pointing
a model at its own failed output biases it toward patching rather than
rethinking, which is wrong for a structural failure. Probably wants
`mode="regenerate"`-style framing after attempt 2.

## 5. `promotion` is collected, capped, stored — and never shown to a downstream node

Grep for `promotion` across the package: it's produced in `v1/writer.py`,
capped in `v1/manifest.py`, written to `manifest.jsonl`, surfaced in the
dashboard, and read back in exactly one place —
`v1/orchestrator.py:_compact_state`, truncated to 120 chars, last 5 lines only,
for a model that is only choosing *which node id to dispatch*.

The writer prompt says: *"This is the only part of your work another node will
ever see."* No other node ever sees it. `build_node_prompt` has no access to
upstream promotions.

This is only latent today because `v2/planner.py` gives every leaf
`depends_on=[]`, so nothing is "downstream." But the moment you wire
dependencies — or just want chapter 7 to know what chapter 6 actually covered —
the handoff channel is disconnected at the consumer end.

**Fix** — `build_node_prompt` reads `manifest.jsonl` and injects the promotions
of `node.depends_on` (and optionally the previous sibling in document order).

**Pros** — closes the loop the writer prompt already promises; ~400 tokens per
upstream node, which is exactly what the cap was sized for.
**Cons** — with `depends_on=[]` everywhere you'd have to choose a heuristic
(document-order predecessor), and a wrong heuristic injects irrelevant context
into every node. Also makes execution order semantically load-bearing, which
currently it isn't — that's a real constraint on future parallel dispatch.

## 6. One orchestrator model call per dispatch, for a decision the harness already made

`v1/orchestrator.py:decide_next_action` computes `ready = tree.ready_nodes()`
in code, sends the model the ready list, and then:

```python
if action == "dispatch" and node_id not in ready:
    node_id = ready[0]
```

The model's only freedom is *ordering within the ready set*. With
`depends_on=[]` on every leaf, all pending nodes are ready simultaneously and
ordering is provably irrelevant to correctness. You are paying one structured
call per node to shuffle a list.

**Fix** — skip the call when `len(ready) == 1`, or when the tree has no edges at
all; fall through to `ready[0]` (which is document order, since `TaskTree.nodes`
preserves the planner's array order).

**Pros** — removes N calls from an N-node run outright.
**Cons** — you lose the escape hatch where a model notices something the
dependency graph doesn't encode. Given the fallback already overrides it
whenever it's wrong, that hatch is narrow — but it does close the door on
smarter scheduling later.

## 7. The orchestrator's context is O(N) per round, so the execute phase is O(N²)

`_compact_state` renders **every node in the tree** every round:

```python
for node in tree.nodes.values():
    lines.append(f"- {node.id} [{node.status}] deps={...} attempts={...} :: {node.brief[:80]}")
```

The module docstring claims *"~2-3K tokens per round regardless of tree size."*
That holds at ~20 nodes. At `DEFAULT_NODE_CAP = 400` it's ~40k tokens per round
× 400 rounds ≈ 16M tokens of orchestrator input for one run, dominating
everything else in the pipeline.

**Fix** — send only ready nodes plus counts by status, not the full tree.

**Pros** — makes the docstring true and the cost linear; combines well with #6.
**Cons** — the model loses the wider picture, which is the only justification
for the call existing at all. If you do #6, this becomes moot.

## 8. `EventLog.last_event` re-parses the whole log; `run_node` calls it three times

`v0/events.py:last_event` calls `read_all()` and scans linearly. `v0/runner.py`
calls it three times per dispatch (`episode_completed`, `node_dispatched`,
`session_captured`). `events.jsonl` grows by ~5 lines per node. For a 400-node
run that's ~1200 full-file parses of a file ending at ~2000 lines.

The dashboard makes it worse: `dashboard/state.py:snapshot()` calls
`read_all()` and hands the result to `subagents()`, and the SSE loop
(`_STREAM_INTERVAL = 1.5`) does this every 1.5 seconds per connected client,
serializing the last 200 events plus the full tree summary regardless of whether
anything changed. The frontend fingerprints the payload to skip re-rendering,
but the server-side parse and the bandwidth are unconditional.

**Fix** — a single `read_all()` per `run_node` call passed down; and on the
server, cache the parsed log against `events.jsonl`'s size+mtime.

**Pros** — mechanical, no behavioral change, no design tradeoff. This is the
cleanest win in the list.
**Cons** — a size+mtime cache is technically defeatable by a same-second
same-size rewrite. `events.jsonl` is append-only and fsync'd, so that can't
happen here — but the cache invariant now depends on that fact, which should be
commented.

## 9. `node.budget` is decorative; every episode gets the same 30-minute wall clock

`v1/tree.py:NodeBudget(tokens=24_000, calls=15)` is set by the planner on every
leaf, persisted in `tree.json`, displayed in the dashboard, threaded through
`v3/repair.py` — and never enforced. The only thing `run_episode` receives is
`types.EpisodeBudget`, which has exactly one field:
`max_duration_seconds: int = 1800`. Every call site in `pipeline/driver.py`
passes a bare `EpisodeBudget()`.

`v2/planner.py:leaf_gate` rejects candidates whose `estimated_calls` exceed
`tool_call_cap=15` — enforcing a cap at plan time that has no runtime
counterpart.

The practical failure mode: a runaway leaf burns 30 minutes and unbounded tokens
against your provider before the harness notices, and `max_tokens:24000` only
catches it *after* the fact, as a gate on output length.

**Fix** — pass `GPTME_CONTEXT_LENGTH` / a step cap from `node.budget` into
`GptmeAdapter` (the `context_length` kwarg already exists and is never used by
`build_writer_adapter`), and scale `max_duration_seconds` with node size.

**Pros** — makes a documented invariant real; caps blast radius per node.
**Cons** — a too-tight cap turns a slow-but-correct node into a hard failure
that burns `max_attempts`, and the token estimate feeding it is a
`words/0.75` heuristic (`v1/gates.py:estimate_tokens`), not a tokenizer. Wants
generous headroom, which limits how much it actually saves.

## 10. `hidden_paths` is dead code, so writers can read the whole run directory

`adapters/cli_agent.py` has a complete mechanism for fencing agents out of
harness state (`hidden_paths`, `_hidden_paths_notice`). Its default is `()` and
**no adapter anywhere passes it** — `GptmeAdapter.__init__` doesn't forward it,
`build_writer_adapter` doesn't set it.

The writer's workspace is the run directory itself with `shell`/`read` in the
allowlist. So a writer can read `events.jsonl`, `approvals.jsonl`,
`audit/<node>.json`, other nodes' `out/*.md`, and other nodes' `scratch/`.

The `audit/` one matters for quality specifically: PLAN.md §3's whole argument
is that a reviewer who can see the writer's reasoning talks itself into
accepting. The inverse leak — a *writer* who can read the reviewer's verdicts
and other nodes' finished artifacts — lets it pattern-match to whatever passed
before instead of doing its own work, which is exactly the drift the frozen
contract exists to prevent.

**Fix** — `build_writer_adapter` passes
`hidden_paths=("events.jsonl", "audit/", "approvals.jsonl", "scratch/", "out/")`
minus the node's own paths.

**Pros** — free, uses machinery already written and already appended to every
prompt.
**Cons** — it's a *prompt-level* fence, not a sandbox; a model can ignore it,
and naming the paths arguably advertises them. A real fix is a per-episode
workspace with symlinks to only what the node needs, which is a much bigger
change to `run_dir` layout.

## 11. Smaller items

**Intake is 8 sequential calls and 7 blocking human round-trips.**
`v2/intake.py` makes one `complete_json` call per entry in `RUBRIC_DIMENSIONS`
(7) to generate *one question each*, then one to finalize. Each blocks on
`approvals.jsonl` polling. Generating all seven questions in one call and
presenting them as one form would cut it to 2 calls and 1 human interaction.
*Cons:* you lose adaptive follow-ups — question 4 currently sees the answers to
1–3, which is genuinely useful for the `exclusions` dimension.

**Survey re-sends 33% of every window.** `window_size=12`, `stride=8` in
`survey_chunks`. The overlap is deliberate (boundary votes near a window edge
are unreliable), but a stride of 10 would cut redundant tokens by half with a
2-chunk overlap that still covers the edge case. *Cons:* fewer duplicate votes
means `assemble_spine`'s highest-confidence-wins merge has less to work with.

**Boundary votes are cast on 15-word previews.** `_render_window` shows
`" ".join(chunk.text.split()[:15])`. For a chunk that starts mid-paragraph
(common — `chunk_text` splits on blank-line runs too) that's not enough signal to
judge whether a new structural unit begins. This is a quality/cost dial, not a
bug; 40 words would roughly triple survey input tokens.

**`complete_json` has no fallback for endpoints that reject `response_format`.**
The docstring says *"Build the fallback regardless"* — and there is one for
malformed *content*, but the request always includes
`response_format: {type: "json_schema", strict: true}`. An endpoint that 400s on
that raises `ProviderError` on the first attempt and never retries without it.
One-line fix: drop `response_format` on retry after an HTTP 400.

**`build_node_prompt` re-reads `contract.md` per node.** Trivial, but it's an
uncached disk read inside the per-node hot path; the contract is frozen by
construction.

## Suggested order

1. **#1** (artifact instruction) — one line, and nothing downstream is correct
   without it.
2. **#2** (materialize spine units) — the second half of "writers can actually
   do their job."
3. **#4** (feed defects into retries) — cheap, uses existing `repair.py` code.
4. **#8** (event log caching) — mechanical, zero design tradeoff.
5. **#6 + #7** (orchestrator) — biggest token saving, one decision to make.
6. **#3** (derive rubrics) — largest scope, and only worth doing once 1, 2 and 4
   are in place, since it multiplies the cost of every failure mode above.
